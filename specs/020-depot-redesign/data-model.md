# Data Model: Depot Page Redesign

**Feature**: 020-depot-redesign
**Date**: 2026-02-12
**Status**: Design Complete

## Overview

This document describes the data model changes required for the depot page redesign. The primary change is adding the `epoch` field to `DepotRollingStockView`. Category reorganization is handled purely in the frontend presentation layer with no backend data model changes.

---

## Backend Data Model (Rust)

### 1. DepotRollingStockView (Modified)

**File**: `src-tauri/src/collecting/domain/depot_view.rs`

**Purpose**: Read-only view of owned rolling stock for depot display

```rust
#[derive(Debug, Clone, Serialize, specta::Type)]
#[serde(rename_all = "camelCase")]
pub struct DepotRollingStockView {
    /// Unique identifier for the owned rolling stock instance
    pub id: OwnedRollingStockId,

    /// Series or class code (e.g., "Class 103")
    pub series_code: String,

    /// Optional road number for identification
    pub road_number: Option<String>,

    /// Optional user-facing friendly name
    pub friendly_name: Option<String>,

    /// Optional depot/storage location
    pub depot: Option<String>,

    /// Rolling stock category (locomotive, EMU, etc.)
    pub category: RollingStockCategory,

    /// Manufacturer display name (e.g., "Hornby")
    pub manufacturer_name: String,

    /// Product code identifying the model variant
    pub product_code: ProductCode,

    /// Optional control type (analogue/DCC)
    pub control: Option<Control>,

    /// Optional livery or paint scheme
    pub livery: Option<String>,

    /// Optional railway company name
    pub railway_company_name: Option<String>,

    /// NEW: Epoch/era (e.g., "IV", "III/IV", "Vm")
    pub epoch: Option<Epoch>,
}
```

**Changes**:

- ✅ Add `pub epoch: Option<Epoch>` field (line ~58)

**Rationale**:

- Epoch is `Option<Epoch>` because not all models may have era information
- Uses existing `Epoch` type (`catalog::domain::railway_model::Epoch`)
- Epoch is a string wrapper (`pub struct Epoch(pub String)`) with validation support

## Database Schema (No Changes)

### Existing Schema

**Table**: `railway_models`

- Contains `epoch` field (type: TEXT)
- Already joined in depot query via `collection_items.railway_model_id`

**Table**: `collection_items`

- Contains `removed_date` field for soft-delete filtering
- Contains `collection_id` for ownership filtering

**Table**: `owned_rolling_stocks`

- Links to `collection_items` via `collection_item_id`
- Stores instance-specific data (road_number, livery, control)

**No migrations needed** - All required data is already in the database.

## Data Flow

### Backend Query Flow

```
1. GetDepot use case
   └─> find_depot_view(collection_id)

2. Repository (find_depot_view)
   ├─> get_owned_rolling_stocks(collection_id)
   │   └─> SQL: Filter by collection_id, removed_date IS NULL
   └─> get_collection_items(collection_id)
       └─> SQL: JOIN railway_models ON railway_model_id
           └─> SELECT rm.epoch (✓ Already fetched)

3. Mapper (collection_item_owned_to_depot)
   ├─> Extract epoch from collection_item.railway_model.epoch
   └─> Build DepotRollingStockView with epoch field
```

### Frontend Display Flow

```
1. Invoke Tauri command: getDepot()
   └─> Returns DepotView { rollingStocks: [...] }

2. DepotState.svelte.ts
   ├─> Group by category using CATEGORY_MAPPING
   │   ├─> locomotives (LOCOMOTIVE)
   │   ├─> railcarsEmuDmu (ELECTRIC_MULTIPLE_UNIT + RAILCAR)
   │   ├─> passengerCars (PASSENGER_CAR)
   │   └─> freightCars (FREIGHT_CAR)
   └─> Apply search filter across all categories

3. +page.svelte
   └─> Render Accordion with 4 sections
       ├─> Each section shows count badge
       ├─> Table includes epoch column
       └─> Sticky headers for scrolling
```

## Validation Rules

### Backend Validation

**Epoch Format** (validated by `EpochKind::try_from`):

- Single: `I`, `II`, `III`, `IV`, `V`, `VI`
- Half: `Ia`, `Ib`, `IIa`, `IIb`, etc.
- Range: `I/II`, `II/III`, `III/IV`, `IV/V`, `V/VI`
- Museum: `Vm`

**Category** (enforced by enum):

- Must be one of 5 valid `RollingStockCategory` values
- Type-safe serialization via serde

**Ownership** (enforced by query):

- Item must belong to collection (`ci.collection_id = ?`)
- Item must not be soft-deleted (`ci.removed_date IS NULL`)

### Frontend Validation

**Search Query**:

- Case-insensitive matching
- Matches against: road_number, series_code, manufacturer_name, product_code
- Debounced 150ms to prevent rapid re-filtering

**Category Mapping**:

- All RollingStockCategory enum values must map to a DepotCategoryKey
- Enforced by exhaustive `CATEGORY_MAPPING` record

## State Transitions

**Depot data is read-only** - No state transitions in domain model.

**UI State Transitions**:

- Accordion sections: Collapsed ⟷ Expanded
- Search filter: Empty → Active → Cleared
- Loading: Idle → Loading → Loaded → Error

## Performance Considerations

### Backend

- **Query Optimization**: Single query with JOIN fetches all data (epoch already included)
- **No N+1 Problem**: All data loaded in one database round-trip
- **Filtering at SQL Level**: `removed_date IS NULL` filter applied in query, not in code

### Frontend

- **Derived State**: Category grouping uses `$derived` for reactive updates
- **Search Debounce**: 150ms debounce prevents excessive re-computation
- **Accordion Virtualization**: Only expanded sections render content
- **Memoization**: Filter results cached by Svelte's reactivity system
