# Architecture for Type-Safe Feature-Based State Management

This document defines the architectural standards for the Rusty Shed application, utilizing Tauri v2, Svelte 5 (Runes), and Specta to ensure a high-performance, type-safe, and modular codebase.

## Technical Stack

- **Frontend**: Svelte 5 (utilizing `$state`, `$derived`, and `$effect`).
- **Backend**: Rust (Tauri v2).
- **Type Bridge**: `tauri-specta` for auto-generating TypeScript interfaces from Rust structs.
- **Pattern**: _Feature-Grouped Domain-Driven Design_ (**DDD**).

## Data Flow Architecture

The application follows a strict data flow to ensure the UI remains in sync with the Rust backend.

| Layer                   | Responsibility                                                                         |
| ----------------------- | -------------------------------------------------------------------------------------- |
| **Rust Domain Modules** | Business logic for Collection, Wishlist, and Depot. Acts as the source of truth.       |
| **Generated Bindings**  | Single file (`bindings.ts`) containing types and command wrappers generated by Specta. |
| **Feature Controllers** | Svelte 5 Classes that hold reactive state and wrap Tauri invoke calls.                 |
| **Context API**         | Scope-limited delivery of Feature Controllers to the component tree.                   |
| **UI Components**       | Reactive display and user interaction via Controller methods.                          |

## Directory Structure

The project is organized by App Feature to prevent scaling issues and ensure modularity.

```

   ├── lib/
   │   ├── bindings.ts             # Auto-generated by Specta (Do not edit)
   │   └── features/
   │       ├── collection/         # Inventory & locomotive management
   │       │   ├── CollectionState.svelte.ts
   │       │   ├── CollectionView.svelte
   │       │   └── ItemCard.svelte
   │       ├── wishlist/           # Future purchase tracking
   │       │   ├── WishlistState.svelte.ts
   │       │   └── WishlistView.svelte
   │       ├── depot/              # Storage & location tracking
   │       │   ├── DepotState.svelte.ts
   │       │   └── DepotView.svelte
   │       └── dashboard/          # Analytics & aggregation
```

## Implementation Requirements

### Rust Structs & Commands

- All shared models must implement `specta::Type` and `serde::Serialize`.
- Tauri commands must return `Result<T, CommandError>` to handle errors gracefully on the frontend.

### The State Controller (Svelte 5 Pattern)

Every feature must have a dedicated controller class inside a `.svelte.ts` file.

- **Privacy**: Use `#` private fields for `$state` variables.
- **Access**: Use `get` keywords for read-only access to state.
- **Encapsulation**: Components must not mutate state directly; they must call class methods (`Actions`).

### Context Pattern

To avoid global state pollution, use the Context Provider pattern per feature:

- Use a `Symbol` for unique context keys.
- Export a `set[Feature]Context` and `get[Feature]Context` helper to ensure type safety when consuming state.

## Quality Standards & Rules

- No `any` Types: All data coming from Tauri must be typed via the generated `bindings.ts`.
- **Naming**: Controllers must follow the `[Feature]State` naming convention.
- **Error Handling**: Every `invoke` in a controller must be wrapped in a try/catch block to manage backend failures.
- **Reactivity**: Avoid `$effect` for data transformations; prefer `$derived` for performance.
